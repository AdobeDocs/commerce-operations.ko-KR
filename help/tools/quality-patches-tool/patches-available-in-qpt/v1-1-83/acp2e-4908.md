# ACP2E-4908: 큰 카탈로그로 인해 과도한 Redis 또는 Valkey 메모리 사용량이 발생했습니다.

ACP2E-4908 패치는 각 저장소 보기의 각 제품에 대해 별도의 레이아웃 캐시 항목이 생성되었기 때문에 큰 카탈로그가 [!DNL Valkey]&#x200B;(또는 [!DNL Redis])에서 과도한 메모리 사용을 초래할 수 있는 문제를 해결합니다. 이 패치는 [[!DNL Quality Patches Tool (QPT)]](/help/tools/quality-patches-tool/quality-patches-tool-to-self-serve-quality-patches.md) 1.1.83이 설치된 경우에 사용할 수 있습니다. 패치 ID는 ACP2E-4908입니다. 이 문제는 Adobe Commerce 2.4.10에서 수정됩니다.

## 영향을 받는 제품 및 버전

**Adobe Commerce 버전에 대한 패치가 만들어졌습니다.**

* Adobe Commerce(모든 배포 방법) 2.4.8-p4

**Adobe Commerce 버전과 호환:**

* Adobe Commerce(모든 배포 방법) >=2.4.8 &lt;2.4.10

>[!NOTE]
>
>새 [!DNL Quality Patches Tool] 릴리스가 있는 다른 버전에 패치를 적용할 수 있습니다. 패치가 Adobe Commerce 버전과 호환되는지 확인하려면 `magento/quality-patches` 패키지를 최신 버전으로 업데이트하고 [[!DNL Quality Patches Tool]에서 호환성을 확인합니다. 패치 검색 페이지](https://experienceleague.adobe.com/tools/commerce-quality-patches/index.html). 패치 ID를 검색 키워드로 사용하여 패치를 찾습니다.

## 문제

각 저장소 보기의 각 제품에 대해 별도의 레이아웃 캐시 항목이 만들어지기 때문에 큰 카탈로그로 인해 [!DNL Redis] 또는 [!DNL Valkey]에서 과도한 메모리가 사용될 수 있습니다.

<u>재현 단계</u>:

1. [!DNL Valkey]&#x200B;(또는 [!DNL Redis])을(를) 기본 캐시 백엔드로 구성합니다.
1. `app/etc/env.php`을(를) 편집하고 cache.frontend.default 블록을 다음으로 설정:

   ```
   'default' => [
       'id_prefix' => '061_',
       'backend_options' => [
           'server' => 'valkey',          // your Valkey/Redis hostname
           'port' => '6379',
           'database' => '1',
           'password' => '',
           'compress_data' => '0',        // key recipe — leaves XML uncompressed
           'persistent' => 0,
           'read_timeout' => 10,
           'connect_retries' => 2,
       ],
       'backend' => 'redis',
   ],
   ```

   `flush: bin/magento cache:flush`.

1. 미디어 성능 고정장치를 생성합니다.

   ```
   bin/magento setup:performance:generate-fixtures \
       setup/performance-toolkit/profiles/ce/medium.xml
   ```


   3개의 웹 사이트 × 3개의 스토어 그룹 × 3개의 스토어 보기, 24K 단순 + 640 구성 가능한 제품, 33개의 속성 세트, 50K 주문을 생성합니다. 빠른 머신에 10분 정도 걸릴 것으로 예상됩니다.

1. [!DNL Valkey] `db1`을(를) 재설정하고 준비:

   ```
   valkey-cli -h <host> -n 1 FLUSHDB
   bin/magento cache:flush
   ```

1. 제품 페이지 샘플 목록을 작성하고 각 URL을 조회합니다.

   ```
   # Build 200 random product URLs across stores 1–4
   mysql -e "SELECT CONCAT(s.code,'|',u.request_path)
             FROM url_rewrite u JOIN store s ON u.store_id=s.store_id
             WHERE u.entity_type='product'
               AND u.request_path NOT LIKE 'catalog/product/%'
               AND s.store_id BETWEEN 1 AND 4
             ORDER BY RAND() LIMIT 200;" magento > urls.txt
   
   while IFS='|' read -r STORE URL; do
       curl -s -o /dev/null "http://<base-url>/${URL}?___store=${STORE}"
   done < urls.txt
   ```

1. `LAYOUT` 캐시 풋프린트를 확인합니다.

   ```
   valkey-cli -h <host> -n 1 --scan --pattern "*LAYOUT_FRONTEND_STORE*" | wc -l
   valkey-cli -h <host> INFO memory | grep used_memory_human
   ```


   고객의 10K 키 / 1.7GB 레제리에 도달하기 위해 크롤링을 확장(또는 `large.xml`/`extra_large.xml` 및 siege/wrk와 같은 실제 로드 도구 사용)하십시오.

<u>예상 결과</u>:

압축이 활성화된 경우 성능에 영향을 주지 않습니다.

<u>실제 결과</u>:

- `LAYOUT_FRONTEND_STORE` [!DNL Redis] 키는 상당한 공간을 사용합니다.
- 새로운 중간 고정장치 설치 시, 200개의 제품 히트 후: 약 564개의 `LAYOUT_FRONTEND_STORE` 키 및 `used_memory_human`(약 20MB)와 약 10MB(제품 페이지당 크롤링 기준) — 약 2.8MB 레이아웃 캐시 키(페이지 히트 전)가 × 상점에 방문한 고유 제품들과 함께 선형적으로 증가합니다.
